# Java concepts used in this project

Every row below points to code that exists and runs. Paths are relative to `src/main/java/com/seismic/`
unless they start with `src/`.

| Concept | Java classes / files | Where it is used | Why it is used | How to explain it during the review |
|---|---|---|---|---|
| **Classes and objects** | `model/Sensor`, `model/SeismicReading`, `model/SeismicEvent`, `model/Alert` | One `Sensor` object per virtual node (15, created from `data/sensors.csv`); one `SeismicReading` per measurement | Models the real-world things the engine reasons about | "`SensorNetworkFactory` reads each CSV row and does `new Sensor(id, name, zone, location)`; the network holds 15 objects with their own state." |
| **Encapsulation** | `Sensor` (private fields, `adjustReliability` clamps to 0–100), `SeismicReading` (private final fields + builder), `GeoPoint` (validates lat/lon), `DatasetMetadata` (counts must add up) | Every model class | Objects cannot get into an invalid state; callers use methods, not fields | "Reliability can only change through `adjustReliability`, which keeps it in 0–100. The constructor rejects a blank sensor ID." |
| **Immutability** | `SeismicReading` (`withQuality`, `withFilteredAmplitude` return copies), `Alert.acknowledge()` returns a new object, records | Validation and filtering; alerts shared between threads | Immutable objects are thread-safe, and the raw reading is never lost | "Filtering does not overwrite the amplitude; it returns a copy with `filteredAmplitude` set." |
| **Interfaces and abstraction** | `repository/*Repository` (6 interfaces) with `jdbc/` and `memory/` implementations; `simulation/ScenarioEffect`; `service/EngineListener`; `CommunicationMonitor.OfflinePenalty` | Services only see the interfaces; `Repositories.jdbc(...)` or `.inMemory(...)` decides the implementation | Same service code for MySQL and demo mode; new scenarios without changing the simulator | "`SeismicEventService` calls `repositories.events().save(e)`; it does not know whether that is MySQL or a HashMap." |
| **Inheritance (only where appropriate)** | `simulation/TimedEffect` (abstract) → `SeismicWaveEffect`, `SingleSensorEffect` (abstract) → `IsolatedSpikeEffect`, `RepeatedFaultEffect`, `NoisyDataEffect`, `InvalidDataEffect`, `CommunicationDropEffect`; `DatasetFormatException extends Exception`; `RepositoryException extends RuntimeException` | Scenario effects share their time-window and target-sensor logic | Real "is-a" relationships with shared code; models use composition instead | "Every single-sensor effect inherits `appliesTo` (right sensor + inside the time window) and only overrides `apply`." |
| **Polymorphism** | `ReadingGenerator.generate` loops over `ScenarioEffect`s and calls `effect.apply(...)` | Each effect changes the reading differently | New behaviour without `if/else` chains | "The generator doesn't know which effect it has; each subclass's `apply` runs." |
| **Enums (with behaviour)** | `SensorStatus.isEligibleForCorrelation()`, `EventSeverity.raisedOneLevel()/cappedAt()`, `SignalLevel.toBaseSeverity()`, `AlertSeverity.fromEventSeverity()`, `EventStatus.isFinal()`, `ReadingQuality`, `AlertType`, `ScenarioType` | Status, severity, lifecycle, quality | Type-safe fixed values, plus logic placed where it belongs | "`EventSeverity` declares NORMAL…CRITICAL in order, so `compareTo` implements the caps." |
| **Records** | `GeoPoint`, `ConfidenceBreakdown`, `ValidationResult`, `DatasetMetadata`, `SimulationRun`, `ProcessingConfig` (+ nested records), `CatalogEarthquake`, `FaultFinding`, `SensorStatusChange` | Value objects and settings | Concise immutable data carriers with validation in the compact constructor | "`ProcessingConfig.DetectionThresholds` rejects `minor >= moderate` when it is built." |
| **Collections Framework** | `ConcurrentHashMap` (`SensorNetwork`), `ArrayDeque` (filter windows, fault history), `LinkedHashMap` with `removeEldestEntry` (bounded alert/event history), `EnumMap` (counts by severity), `TreeMap` (sorted statistics), `HashSet` (duplicate IDs in CSV import), `List`/`Map`/`Set` everywhere | Sensor lookup, moving average, history, statistics | Right structure per job: O(1) lookup, FIFO window, bounded memory, sorted output | "The moving average is an `ArrayDeque` per sensor: add at the end, remove from the front when it exceeds 3." |
| **Queue / PriorityQueue** | `AlertManager.unacknowledged` (`PriorityQueue` by severity then age); `LinkedBlockingQueue` between simulator and processor | Most-urgent alert on the Alerts screen; producer-consumer hand-over | `peek()` gives the most urgent alert in O(1); the bounded queue applies back-pressure | "CRITICAL alerts are always at the head of the priority queue regardless of arrival order (`mostUrgentAlertComesFirst` test)." |
| **Generics** | `FxTasks.run(Callable<T>, Consumer<T>, Consumer<Throwable>)`, `JdbcSupport.SqlWork<T>` / `inTransaction<T>`, `UiFormat.column<S,T>(Function<S,T>)`, generic collections | Background tasks, transactions, table columns | One type-safe helper for many result types | "`inTransaction` returns whatever the lambda returns: the saved `DatasetMetadata`, or nothing." |
| **Lambdas, functional interfaces, streams** | `Comparator.comparing`, `Collectors.groupingBy` (`DatasetStatisticsService`), `Supplier<String>` IDs, `Consumer<EngineListener>` | Statistics, sorting, callbacks | Concise data processing | "`groupingBy(SeismicReading::getSensorId, TreeMap::new, toList())` builds the per-sensor statistics." |
| **Exception handling** | Checked `DatasetFormatException`, `IOException`; unchecked `RepositoryException`; try-with-resources (files, JDBC); catch-and-continue in `SensorSimulator.sampleSafely` and `SeismicEventService.processLoop`; `DatabaseConnection.friendlyMessage` | CSV import, JDBC, background threads | Bad input never crashes the app; errors become dialogs or alerts; credentials never shown | "A row with a bad timestamp becomes a `RejectedRecord` with its line number. The load continues and the user sees the reason." |
| **File handling and CSV processing** | `dataset/CsvUtils` (quoted fields), `CsvDatasetLoader`, `UsgsCatalogLoader`, `CsvExporter`, `DemoDatasetGenerator`, `SensorNetworkFactory`, `ConfigLoader` | Load, import and export datasets; read config | Data lives in real files, not hard-coded arrays | "`CsvUtils.parseLine` handles `\"10 km N of X, Y\"` in the USGS file, which a plain `split(\",\")` would break." |
| **Multithreading** | `SensorSimulator` (4 worker threads, 15 periodic tasks), `SeismicEventService` (`event-processor`, `persistence` threads), `FxTasks` (`ui-worker`) | Live monitoring | Sensors report independently; DB and UI never block detection | "Three kinds of thread: producers (sensors), one consumer (processing), one writer (DB). See the thread table in architecture.md." |
| **ExecutorService and scheduled tasks** | `Executors.newScheduledThreadPool` + `scheduleAtFixedRate` (`SensorSimulator`); `newSingleThreadExecutor` (processing, persistence); `newFixedThreadPool` (`FxTasks`); `shutdown` + `awaitTermination` | Start/Stop/Reset/close | Managed thread pools with clean shutdown, no stray threads (`allSensorsReportConcurrentlyAndStopCleanly`) | "Stop calls `shutdown()` and waits up to 2 s; the test checks no `sensor-sim` thread is still alive." |
| **Synchronization and thread-safe collections** | `synchronized` methods in `Sensor`, `AlertManager`, `SensorSimulator.start/stop`, in-memory repositories; `CopyOnWriteArrayList` (active effects, listeners); `ConcurrentHashMap`; `ConcurrentLinkedQueue` (`LiveDataBridge`); `AtomicLong`/`AtomicInteger`/`AtomicBoolean`; `volatile` flags | Data shared by simulator, processor, DB and UI threads | Prevent races and torn reads; the pipeline itself is confined to one thread so the algorithms need no locks | "The UI acknowledges an alert while the processor raises one; both methods are `synchronized` on the same `AlertManager`." |
| **JDBC** | `database/DatabaseConnection` (`DriverManager`), `repository/jdbc/*`, `PreparedStatement`, `ResultSet`, batch inserts (`addBatch`/`executeBatch`), generated keys | All persistence | Standard Java database access | "Every value is a `?` parameter, so there's no SQL injection; every connection/statement/result set is in try-with-resources." |
| **SQL: joins, indexes, transactions, constraints** | `src/main/resources/db/schema.sql` (7 tables, FKs, CHECKs, indexes); joins in `JdbcReadingRepository.CONTRIBUTING`, `JdbcEventRepository.SELECT_ASSOCIATIONS` and `COUNT_PER_SENSOR` (LEFT JOIN + GROUP BY); `JdbcSupport.inTransaction` | Event history, contributing readings, statistics, dataset save | Normalised data with integrity and fast lookups | "Saving a dataset is one transaction: a failing reading rolls back the metadata too (`datasetIsSavedInOneTransactionOrNotAtAll`)." |
| **JavaFX** | `Main` (`Application` lifecycle), FXML in `src/main/resources/fxml`, CSS `css/app.css`, `TableView`, `LineChart`, `BarChart`, `Canvas` (`ui/SensorNetworkCanvas`), `ListView`, `ProgressBar`, `FileChooser`, `TabPane` | Whole user interface | Desktop UI as required | "The map is a `Canvas`: lat/lon are projected to pixels, sensors drawn as circles coloured by status." |
| **Event-driven GUI programming** | `onAction="#onStart"` handlers, property listeners (`runningProperty`), `selectedItemProperty` listeners, `setOnMouseClicked` on the canvas, `Timeline` refresh | Buttons, selection, map clicks, live refresh | The UI reacts to user and engine events | "Clicking a sensor on the canvas finds the nearest sensor and selects it in the table." |
| **Thread-safe UI updates** | `ui/LiveDataBridge` (background → `ConcurrentLinkedQueue` → `Timeline` on the FX thread), `ui/FxTasks` (`javafx.concurrent.Task` callbacks), `Platform.runLater` in `SimulatorControlsController.onReset`, `Application.init()` for DB connection | Every live update | Controls may only be touched on the JavaFX thread | "Engine threads never touch a control; they drop data into a queue that the FX thread drains every 500 ms." |
| **Separation of concerns / layers** | `model` → `processing`/`simulation`/`dataset` → `service`/`alert` → `controller`/`ui`; `repository` + `database` | Package structure | Each layer testable and replaceable on its own | "Controllers have no SQL or algorithms; processing classes have no I/O, so they're tested with plain objects." |
| **Repository and service layers** | `repository/*`, `service/SeismicEventService`, `service/DatasetService` | All data access and use cases | Clear API for the UI; storage hidden behind interfaces | "`DatasetService.analyze` = replay + transactional save + publish to history, in one method the controller calls." |
| **Dependency injection (constructor)** | `AppContext` (composition root), `ui/ControllerFactory` (FXML controllers built with their services) | Start-up | No global state; objects receive what they need | "`ControllerFactory.call` builds `new DashboardController(bridge)`; FXML uses it through `setControllerFactory`." |
| **Builder pattern** | `SeismicReading.Builder` | Readings with many optional fields | Readable construction | "`SeismicReading.builder().sensorId(\"S01\").amplitude(0.4)...build()`" |
| **Unit testing (JUnit 5)** | `src/test/java/...` (17 classes, 108 tests): `@Test`, `@BeforeEach`, `@BeforeAll`, `@TempDir`, `@EnabledIfEnvironmentVariable`, `assertThrows`, `Assumptions` | All algorithms, loader, repositories, threads | Proves behaviour; deterministic (fixed seeds, explicit time) | "`CommunicationMonitorTest` passes timestamps instead of sleeping, so a 5 s timeout is tested instantly." |
| **Logging (SLF4J + Logback)** | `LoggerFactory.getLogger(...)` in services/simulator; `src/main/resources/logback.xml` | Start-up, scenario activation, status changes, errors | Diagnosable behaviour without `System.out` | "`logs/seismic-engine.log` shows every status change with its reason." |

## Optional / future improvements (NOT implemented)

These are ideas only; nothing in the code claims them:

* Connection pooling (e.g. HikariCP) instead of one `DriverManager` connection per operation.
* Proper epicentre location (grid search on arrival times) instead of "first-triggering sensor = origin".
* Separate P- and S-wave picking (STA/LTA) on continuous waveforms instead of per-reading amplitudes.
* Calibrating confidence weights against labelled data (precision/recall over many generated datasets).
* Role-based users and audit of who acknowledged an alert.
* Module system (`module-info.java`) and `jlink`/`jpackage` installers per operating system.
